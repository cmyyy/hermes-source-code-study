# 飞书里的 markdown：一条消息只能选一种格式时的取舍

> 源码位置：`plugins/platforms/feishu/adapter.py` → `_build_outbound_payload()`、`_build_markdown_post_payload()`
> 研读版本：hermes-agent v0.19.0（commit d71033a40）

## 这是什么 / 解决什么问题

Hermes 在飞书里回复含 markdown 表格的内容时，会把整条消息降级为纯文本发送——标题、加粗等格式符号原样裸露（`## 标题`、`- **加粗**`），而不是渲染成富文本。这不是没做完的 bug，而是飞书消息协议限制下的一个**明确取舍**：宁可符号裸露，也不能让内容整块消失。

## 为什么这么设计

- **一条消息只能选一种格式，是协议硬约束**。`_build_outbound_payload()` 用三个互斥分支决定消息类型：检测到表格（`_MARKDOWN_TABLE_RE`）→ 强制纯文本；检测到 markdown 符号（`_MARKDOWN_HINT_RE`）→ 转飞书 post 富文本；都没有 → 纯文本。飞书消息的 `msg_type` 是单一值，不存在"一半富文本一半纯文本"的中间态，所以必须给"格式优先级"排个序。

- **表格的优先级最高，因为 post 富文本不渲染表格**。代码注释写得很直白：Feishu post-type 'md' elements do not render markdown tables; sending table content as post causes the message to appear blank on the client。也就是说，如果含表格的内容走 post 格式，用户在客户端看到的是**整块空白**——比"符号裸露"糟糕得多。**"保证用户至少看得到文字"优先于"格式好看"**，这是内容可用性对美观的让步。

- **标题正则故意要求 `#` 后必须有空格**。`_MARKDOWN_HINT_RE` 用 `(^#{1,6}\s)` 而非 `(^#{1,6})`，避免把 `#hashtag`、`#12345` 这类合法文本误判成标题。而且匹配正则必须与剥离正则（`_RE_HEADING`）保持同一规则——否则会出现"发送时认了是标题、降级时没剥掉"的错位 bug，比不认更糟。

- **理想方案存在，但成本高**。真正的解法是分块发送：把回复拆成多段，标题/加粗段落走 post、表格走 text、代码块走 post，`_build_outbound_payload` 返回 `list[tuple[str, str]]` 逐段发。或者干脆用飞书卡片消息（Card，支持表格和复杂布局），但要重写整个适配器。**当前实现是"一行正则换可用性"的快路径，是工程上成本与体验的权衡**——先把问题挡住，再等值得投入的时机做重构。

- **降级的影响面是渐进的，取舍因此成立**。纯文字回复正常渲染富文本；纯表格降级为纯文本仍可读；只有"标题/加粗 + 表格"混排时，表格之前的 markdown 符号才会原样裸露——受影响的是一条回复里的局部，而不是所有回复。**用局部格式损失换全局内容可见**，这个代价在协议限制下是划算的。作者把"分块发送""飞书卡片消息"等更优方案都记录在案（`_build_outbound_payload` 改为返回 `list[tuple[str, str]]` 逐段发），作为明确的重构债，而不是假装问题不存在。同时，这个案例也提醒适配器开发的一个通用原则：**对接平台能力时，先确认平台渲染器的边界，再决定消息格式策略**——很多"渲染问题"其实是协议能力问题。

## 关键机制/流程

```
回复内容
  → 含表格？          → 纯文本发送（保底：格式符号裸露，但内容可见）
  → 含 markdown 符号？ → post 富文本（标题/加粗/列表渲染）
  → 都没有            → 纯文本发送
```
